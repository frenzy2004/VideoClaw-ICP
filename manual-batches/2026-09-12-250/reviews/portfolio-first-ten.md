## Blocking corrections

### B1 — c5-014: define what pausing does to the count before using it to admit urgent work

Files and passages:

- `drafts/portfolio-media-platform/portfolio-media-review-work-limits.md`, lines 15–21: entry occurs when a reviewer receives a version; exit occurs when the decision is recorded; the text then permits formally pausing a commitment.
- Same file, line 29: a full queue can admit work after identifying what will “finish, move or be explicitly displaced.” Lines 35–49 set a three-item limit, include blocked Beacon, and say: “If Ember requires an interruption, record which active item is paused and notify its company.”
- `drafts/portfolio-media-platform/portfolio-media-review-work-limits.json`, lines 23–24: the FAQ asks whether blocked reviews count, but answers only that the commitment must remain visible and may be formally paused.

Why this blocks: the article's central job is deciding whether another item may enter. The ordinary completion case is understandable, but the urgent branch never gives a reproducible count or says whether the limit governs all unfinished reviews or only a narrower set receiving active attention. A paused, unfinished review has not met the article's own exit condition. Merely keeping it visible does not establish that admitting Ember respects the limit. The cited Kanban Guide counts started-but-unfinished work as WIP and requires explicit exception policies (S3). This is an under-specified operating rule, not evidence that the draft fabricated its source quotation.

Required correction: state directly whether blocked/paused items count, distinguish any separate active-attention limit from total review WIP, and show the urgent branch's before/after counts. If admitting Ember raises unfinished reviews from three to four, identify that as an explicit temporary exception with an ending condition; alternatively show which decision actually finishes first. Make FAQ 1 answer the counting question. Preserve company-specific reviewer constraints: the coordinating editor's illustrative limit must not imply that company approvers are interchangeable.

### B2 — c5-020: make the example queries answerable by the supplied dictionary

Files and passages:

- `drafts/portfolio-media-platform/portfolio-media-library-tag-taxonomy.md`, lines 27–36: dictionary includes company, asset type, subject, release state, audience, language, related asset and description. Release examples are working, company-approved and archived.
- Same file, lines 44–53: asks the reader to create fictional assets, then maps “Find Alder's current founder headshot” only to “Company, type, release state.” No populated asset records or expected result IDs are supplied. The final query calls a field “archive state,” whereas the dictionary calls it “Release state.”
- `drafts/portfolio-media-platform/portfolio-media-library-tag-taxonomy.json`, line 3 describes “six retrieval tests”; lines 65–66 also promise testing against a labeled sample.

Why this blocks: company + portrait + company-approved can match an employee portrait, multiple founders, and an older approved portrait. Those fields alone do not establish the subject's identity/role or which approved version is current. The separate description field could help, but the example does not use it or define a reliable current-version reference. The main practical output therefore asserts a discriminating search it has not demonstrated. S13 and S14 support search-oriented taxonomy and tags, not this particular mapping's correctness.

Required correction: add a small filled set of fictional asset records, map each of the six questions to actual fields/values, and show expected asset IDs plus at least one excluded near-match. Either narrow the headshot question to what the supplied fields can establish, or add/use verified subject information and a reference to the current released asset. Keep release authority in its existing record rather than expanding into c5-021's separate version-control job. Use one consistent field name for archived state. This is a content correction, not a request to implement a search system.

The exercises themselves differ materially. The exact-paragraph and 16-word-span comparison within these ten found no repeated substantive prose. The bare download CTA makes no feature promise, but the portfolio operations-to-desktop-app connection is weak. Strengthen only with verified product context; do not invent portal, DAM, scheduling or automation capabilities.
7. **Evidence boundaries:** FAQs are labeled editorial, not PAA or verbatim source answers. Several sources provide context rather than independently tested portfolio outcomes, especially First Round/a16z and the Canto-to-directory adaptation. No search-volume, difficulty, CPC, ranking or competitor-gap claim was verified here. Intent distinction is not proof of search demand.
