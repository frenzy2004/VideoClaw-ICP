Test portfolio media findability by giving people realistic tasks and observing where they look, what they search for and whether they recognize the right resource. Record the route, not just success or failure. A small task-based test can reveal unclear labels, hidden links, missing guidance and resources that no longer answer the question.

## Start with a real retrieval task

A media portal can be neatly organized and still be difficult to use. Operators know the names of workshops, collections and internal programs. A founder may only know the problem: “I need the approved photo for tomorrow’s speaker announcement.” Testing navigation alone misses that gap between organizational language and user intent.

[Atlassian’s guidance on knowledge self-service](https://www.atlassian.com/itsm/knowledge-management/self-service-success) discusses findability and maintaining useful resources. For a portfolio media program, turn that broad concern into observable tasks. Ask someone to locate an answer they could actually need, using their normal starting point and permissions.

Avoid tasks that reveal the solution. “Open the press-kit folder and download the headshot” tests compliance with directions. “Find the headshot you are allowed to send to a conference organizer” tests discovery, interpretation and confidence. Write the intended outcome separately so the facilitator does not accidentally coach the participant toward it.

## Build a five-task test card

Choose tasks that cross different resource types and company contexts. Include one approved asset, one learning resource, one support route, one template and one answer that should not be available to the participant. That last task checks whether the portal explains an access boundary without leaking another company’s material.

Use fictional company names in the test plan, but test real approved resources with authorized participants. The following card is an original example, not a claim about how founders typically behave.

| Task prompt | Expected destination | What to observe |
| --- | --- | --- |
| Find Alder’s current approved founder portrait | Company portrait record | Can the user identify the current approved copy? |
| Find help preparing a customer interview | Relevant workshop or guide | Does the title describe the problem clearly? |
| Ask for feedback on a rough video | Correct support request route | Can the user distinguish advice from production help? |
| Find the latest speaker slide template | Active shared template | Is an outdated copy easier to discover? |
| Find a private Beacon session recording | A clear restricted-access explanation | Does the user understand why it is unavailable? |

Add a starting location, participant role, expected evidence of completion and an optional stopping condition for each task. Do not set an arbitrary speed threshold and call it a usability standard. The first useful evidence may be a repeated misunderstanding rather than elapsed time.

## Observe the route without rescuing it

Invite a mix of people who differ in familiarity with the program. A recent joiner and a long-standing operator may use different routes. Keep observations attached to roles and situations rather than treating a tiny convenience sample as representative of the portfolio.

Ask participants to describe what they expect before clicking or searching. Note their exact search terms, the first route attempted, places where they backtrack, and the evidence they use to decide that a result is correct. If they ask the facilitator for help, record that request before offering assistance.

Capture the result in a route log: task, starting point, search or navigation sequence, destination chosen, confidence, help required and observed obstacle. Separate what happened from why you think it happened. “Opened last year’s template first” is an observation. “Does not understand versioning” is an interpretation that requires further checking.

Do not record sensitive screens or private conversations simply to make the test easier to analyze. Use the program’s agreed research process and collect only the information needed for the task. A written route log can be sufficient for a bounded operational review.

## Diagnose the type of failure

A failed task does not automatically mean the search engine needs replacement. Distinguish a vocabulary problem from a navigation problem, an access problem, a missing resource and an unclear answer. Each requires a different intervention.

[Bynder’s taxonomy guidance](https://support.bynder.com/hc/en-us/articles/20331272932626-Taxonomy-Tips-for-your-DAM) encourages learning from user search terminology. Apply that idea narrowly: when participants search for “headshot” but the library uses “executive portrait,” test an additional user-facing label or search term. Do not redesign the entire taxonomy from one observation.

A navigation problem might appear when everyone starts from the cohort page but the only support link lives in an administrator handbook. A recognition problem appears when the right resource is found but its approval or currency is unclear. A missing-content problem appears when no resource actually answers the task, even though the search results look plausible.

Create a diagnosis column with an evidence note. “Likely vocabulary mismatch: two participants searched for headshot and did not recognize portraits” is more useful than “search is bad.” Keep alternative explanations visible until a repair has been tested.

## Turn findings into bounded repairs

Choose a small set of repairs that directly address observed obstacles. Assign each an owner and a retest task. A useful repair changes the experience at the point of failure, not merely the internal documentation explaining why the portal is organized that way.

For the fictional template task, suppose the retired deck appears before the active deck and both are titled “Speaker template.” The repair could add a current label and a replacement link to the older record, then remove the retired copy from the everyday resource page. The retest asks someone to find the latest template without mentioning those changes.

For the support task, a founder may choose a production request form when they only need editorial advice. The repair could clarify the two routes with concrete examples. This is not evidence that the program needs more production capacity; it is evidence that the entry point did not communicate the distinction.

Record repairs that cannot be made immediately. If a resource belongs to a company that has not approved wider sharing, the answer may be a clear access explanation or an alternative public guide. Findability work should not expand access just to make a task succeed.

## Retest the same job and preserve the evidence

After the repair, repeat the underlying task with someone who has not memorized the previous route where practical. Keep the goal and starting context comparable. Changing the task to match the new label can create the appearance of improvement without testing whether the original problem was resolved.

Compare routes, interpretation and help required. Report findings descriptively: “The participant found the active template from the cohort page and identified its approval date.” Avoid presenting a small test as a portfolio-wide adoption rate or a predicted business outcome.

Close each finding with the original observation, chosen repair, retest evidence and remaining uncertainty. This produces a compact findability backlog grounded in actual retrieval jobs. Revisit it when the portal gains a new resource family, changes navigation or serves a different cohort. The purpose is not to prove the library is intuitive; it is to discover where useful media support remains difficult to reach.
