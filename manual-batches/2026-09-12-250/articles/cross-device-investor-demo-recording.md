Record a cross-device investor demo by capturing both sides of the same product interaction and aligning them around a shared event. Keep the input and result identifiable across screens, preserve actual waiting time or disclose edits, and choose a layout that makes the relationship readable rather than merely showing two devices.

## Define the event that crosses between devices

Choose one cause-and-effect relationship. A dispatcher sends an assignment from a desktop, and a technician receives it on a phone. A user approves something on mobile, and the desktop view changes. The connection between those states is the demonstration.

Write down which device initiates the event, which receives it, and what confirms the relationship. Use a harmless shared identifier or another visible property that survives the transfer. Two screens showing similar-looking records are not enough if the viewer cannot tell they concern the same item.

Identify the account roles and starting state on both devices. Do not begin with the recipient already displaying the final result unless that is explicitly an opening preview. Restore the actual scenario before capturing the run.

This task is a recorded cross-device flow, not live phone projection at an event. Plan the source captures and their synchronization first; the final movie can then be played through a separate presentation setup.

## Capture each screen with a tested local method

Choose a recording route for each device that preserves the useful image. For an iPhone connected to a Mac, [Apple documents recording the device screen in QuickTime Player](https://support.apple.com/en-eg/guide/quicktime-player/qtp356b55534/mac). Use the supported capture route for your actual device and operating system.

Make a short test from each source and open the saved files. Confirm that the decisive interaction appears, the image orientation is correct, and any required sound is present. A successful preview does not prove the saved capture contains the same material.

If the desktop also hosts the phone capture, make sure your desktop recording does not accidentally include the capture controls or a recursive preview. Define the application region you intend to show and test the combined recording load before the real run.

Keep source files separate where possible. A single composite recorded too early can lock in unreadable proportions or hide a detail you later need. Separate sources give you room to frame the final evidence without changing the underlying event.

## Establish a shared event marker and preserve one run

Start both recordings before the product action. Use a common visible or audible marker that the sources can genuinely capture, or align them with a clearly identifiable event present in both records. Do not assume two devices' displayed clocks are synchronized.

For a fictional assignment flow, the run might use job J-17 and a distinctive change from “unassigned” to a named fictional technician. The identifier connects the content, while a common capture reference helps align the recordings in time. These are related but different jobs.

[Apple describes synchronizing same-take clips](https://support.apple.com/en-ie/guide/final-cut-pro/verc1fabc30/mac). After using an automatic or manual alignment method, inspect an actual shared event to confirm the match.

Keep both sources running through the result. Do not pause one recording during a wait while leaving the other running and later treat their timelines as equivalent. If a source drops out, mark that run and decide whether a fresh capture is needed.

## Build a two-lane event sheet

Map what each device shows at the important moments. The sheet makes it easier to distinguish real product delay from a synchronization mistake.

| Event | Desktop source | Mobile source | What must remain clear |
| --- | --- | --- | --- |
| Starting state | Fictional job is unassigned | Recipient has no assignment | Result does not pre-exist the action |
| Initiation | Dispatcher submits the assignment | Recipient remains visible | Which device caused the change |
| Transfer interval | Actual post-submit state | Actual waiting state | Any removed time is disclosed |
| Result | Job shows the new assignee | Same job appears for technician | Both views concern the same item |
| Confirmation | Relevant final desktop state | Technician opens the job | The result is inspectable |

Use actual source timecodes when applying the sheet. If the recordings have different start times, write both source positions rather than inventing one shared timecode.

Do not infer network performance from the difference between two unsynchronized videos. A timing claim needs an appropriate measurement, not an editor's guess about alignment.

## Choose simultaneous or sequential presentation by readability

Side-by-side playback can make causality visible, but it gives each screen less space. Use it when the important details remain readable at the intended viewing size. A portrait phone beside a wide desktop may need an asymmetric layout rather than equal halves.

Sequential playback can work when it preserves the connection. Show the initiating action, identify the recipient view, and show the corresponding result. Keep the shared fictional identifier visible and disclose any time jump.

You can combine approaches: briefly show both devices to establish the relationship, then enlarge the receiving screen for inspection. Make the transition deliberate so the viewer understands that the close view is the same run.

Avoid a decorative phone frame if it makes the useful screen too small. The investor needs to inspect the product behavior, not admire a device mockup. Label the device or role in plain text when that is enough to preserve context.

If one source is a reconstruction or a different run, label that explicitly. Do not let a polished split-screen imply simultaneous capture when the events were recorded separately.

## Check causality, continuity, and the final result

Watch the export without narration first. Can you identify which action started the change and where the corresponding result appears? If not, adjust framing, labels, or the selected sequence before adding more explanation.

Then listen with the picture. The founder's language should match the captured timing and scope. Avoid saying “instantly” when the movie removed a wait or “automatically” when the operator performed an omitted action.

Keep the complete source pair and the event sheet together privately. Use a run identifier in both filenames so a later editor does not pair the desktop from one attempt with the phone from another. Preserve the start offsets and any disclosed edits in the notes.

A useful cross-device demo ends with an inspectable connection: this action on this device produced this result on the other under the stated conditions.
