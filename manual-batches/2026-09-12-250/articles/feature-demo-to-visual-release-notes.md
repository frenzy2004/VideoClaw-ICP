Turn a feature demo into visual release notes by showing what changed, who the change affects and what the user should do next. Reuse the relevant interaction from current footage, preserve availability limits, and add a concise text companion. Existing customers need a clear update rather than another introduction to the whole product.

## Name the change in the user’s workflow

Begin with the behavior that changed. “The review panel has a new layout” describes a product update. “Reviewers can find the request and its actions together” explains why a user might care. Use the second kind of sentence when it accurately describes the change.

List who is affected and who is not. An update may concern administrators, a particular workspace configuration or people using one workflow. Avoid presenting a limited release as universally available. If availability is not confirmed, resolve that before writing a definitive instruction.

Wistia’s [Customize panel announcement](https://updates.wistia.com/publications/find-and-apply-customizations-more-easily-with-a-redesigned-customize-panel) offers a concrete publisher example: it contrasts the previous arrangement with the new organization. You can learn from that explanatory structure without copying its wording or treating its product details as your own.

Choose one change for the video. Related changes can be mentioned in the text, but a clip that tries to explain an entire release may leave current users unsure which action they need to take.

## Select a complete before-and-after interaction

Find the current demonstration that shows the changed behavior. Identify the setup, the action and the settled result. If older footage is available and appropriate, compare it with the current interaction. Otherwise use a clearly labeled written description of the previous behavior rather than fabricate an old interface.

Keep the comparison fair. Use equivalent examples and avoid making the old workflow look unnecessarily confusing. The purpose is to orient existing users, not dramatize a before-and-after story that the product does not support.

Check the recording environment. A demo account may have a setting or feature that some customers do not yet have. Preserve the relevant condition in the release note and avoid presenting a staged example as an account-specific result.

Decide whether the original narration remains useful. It may include a long product introduction that current users do not need. Remove that setup only after supplying the context required to understand the changed action. The video should remain clear when played directly from an email or update page.

## Use a visual release-note storyboard

This original storyboard uses a fictional task-review update. It is an example of explanatory structure, not a claim about any named product.

| Beat | Visual content | Text companion |
| --- | --- | --- |
| Previous behavior | A reviewer navigates away to find the request | “Previously, the request and decision were in separate views.” |
| Changed interaction | The request appears beside the decision controls | “The review view now brings these items together.” |
| Practical effect | The reviewer reads the request before choosing an action | “Check the request here before completing the review.” |
| Availability | A clearly labeled setup note | “Confirm that this update is enabled for your workspace.” |
| Next step | The current destination or relevant help page | “Open a sample request and inspect the new view.” |

Replace every placeholder with verified product information. Do not publish the availability wording as a substitute for checking the actual release state.

The storyboard keeps the update focused on user orientation. It also gives the editor a clear test: each shot should explain a specific difference or action, rather than simply show attractive interface motion.

## Edit the update around the changed action

Keep the clip’s opening direct. State the change, show the relevant control and demonstrate the result. Existing customers may recognize the product immediately, so a long branded introduction can delay the information they came for.

Remove unrelated clicks and waits when doing so does not conceal an important dependency. If the new workflow requires a prerequisite, include it in the text or the video at the point where it matters. Do not imply that a multi-step setup has disappeared merely because you cut it from the demonstration.

Loom’s [video-stitching announcement](https://www.atlassian.com/blog/loom/video-stitching) illustrates explaining a feature through concrete uses such as updating an existing recording. Treat it as a historical communication example, not a current plan or capability recommendation.

Use annotations sparingly. A label such as “New location” can orient someone who knows the old interface. Avoid covering the very control the viewer needs to find. Pause long enough on the result for the intended display context, then test the actual exported clip.

## Write a text companion that answers practical questions

The written release note should help people who skim, cannot play the video or need to return later. State the change, the affected audience, any prerequisite and a clear next action. Link to detailed documentation when the update introduces a procedure too complex for the short note.

Use a title that names the user-visible difference. “September improvements” may belong on a release index, but the individual item should help a reader recognize whether it concerns them. Avoid promising benefits that the footage does not establish.

Separate shipped behavior from planned work. If the team wants to mention a future improvement, keep it clearly distinct and do not make the current demonstration appear to include it. The same applies to a limited rollout or optional setting.

Check the video and text together. They should use the same names for controls and the same account of availability. A correct clip paired with an outdated paragraph can still mislead a user trying to apply the change.

## Test the update with someone who knows the old version

Ask a colleague familiar with the previous workflow to watch the clip and read the note. Then ask them to explain what changed, whether it affects them and what they would do next. Their answers reveal whether the update supplies enough orientation.

Also test with someone who has not used that feature. They do not need a complete product lesson, but they should understand the basic purpose of the change. If they cannot, add a brief definition rather than expand the clip into a full tutorial.

Verify the destination and the product state immediately before release. A link can move, a label can change or an availability condition can be revised after the original recording. Keep the source footage and the final note connected so later corrections are straightforward.

When support questions arrive, use them to improve the explanatory gap. If users ask where the control moved, improve the visual orientation. If they ask why the option is missing, clarify availability. These are different problems and should not receive the same generic update.
