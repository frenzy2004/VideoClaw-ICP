Update an old product video by identifying exactly which claims, interface states, or steps are outdated, then replacing only the segments whose meaning has changed. Preserve still-useful footage and check the joins, captions, chapters, and distribution links. Choose the publishing replacement method deliberately because hosts handle versions and analytics differently.

## Separate cosmetic age from incorrect instruction

Watch the existing recording with the current product open beside it. Mark differences, but do not assume every visual mismatch requires a new shoot. A changed accent color is different from a button that moved, a renamed action, or a workflow that no longer exists.

Classify each issue by its effect on the viewer. Cosmetic differences may be acceptable if the action remains easy to recognize. Navigation changes can make an otherwise accurate tutorial difficult to follow. A changed product behavior or unsupported claim needs a substantive correction.

Write the exact failure: “The recording tells viewers to open the old export menu, but export now starts from the report toolbar.” That is a repairable segment. “The video feels dated” is too vague to guide a bounded update.

Check the intended audience and task before deciding scope. A general product overview may tolerate more visual variation than an exact setup tutorial. Do not recapture an entire explanation if only one action has changed, but do not preserve familiar footage that now teaches the wrong process.

## Create a segment repair map

Use this fictional example for an expense-reporting product. The original recording still explains report preparation well, but the export workflow and a status label have changed.

| Segment | Current problem | Repair type | Dependency |
| --- | --- | --- | --- |
| Opening explanation | Still accurate | Keep | None |
| Report selection | New visual style, same action | Keep after readability check | Mention only if confusing |
| Export step | Control moved to a toolbar | Replace screen segment | Update narration and captions |
| Completion state | Status label renamed | Replace result frame and spoken term | Check later summary |
| Closing resource | Link points to retired help page | Update destination and visible reference | Verify published page |

Add start and end times from the actual cut, plus the last valid state before the replacement and the first valid state after it. Those boundaries determine whether new footage can join cleanly.

The map should also identify uncertainty. If nobody has verified a product behavior, do that before recording. A polished replacement based on an assumption only creates a newer version of the same problem.

## Capture the smallest complete replacement

Record enough context to make the changed step understandable. Include the starting state, the action, and the resulting state, with a little extra room around both ends for editing. Do not capture only a cursor click if the viewer needs to see which report is selected.

Match the existing framing where practical: screen scale, window size, pointer visibility, and sample data. Exact visual imitation is less important than continuity, but abrupt shifts can distract from a small update.

If narration changes, record the complete sentence or thought rather than replacing a single word in a way that sounds unnatural. Match the meaning first, then adjust pacing and audio consistency. Avoid compressing a longer new explanation until it becomes difficult to follow.

[Atlassian’s video-stitching article](https://www.atlassian.com/blog/loom/video-stitching) describes combining recorded sections, including updates to existing material. Use that as a reminder that the source recording can be modular in practice; the repair still needs a coherent before-and-after state.

Keep sample information consistent across the join. A report total or account name that changes unexpectedly can make viewers think they missed an important action.

## Repair the surrounding explanation

Insert the replacement and watch the preceding and following passages together. Listen for references that no longer make sense: “the button on the left,” “the same status as before,” or “this takes us back to the old menu.” A local interface change can affect narration outside the visible replacement.

Check captions against the new audio. Old caption files may remain attached even when the video changes. Review any title card, thumbnail, transcript, and written instructions that show the retired term or interface.

Rebuild chapter times if the replacement changes duration. Also inspect known timestamp links in sales messages, help pages, or related resources. A stable watch URL does not guarantee that an old time offset still reaches the intended answer.

Use a continuity pass focused only on meaning. Ignore minor color differences for that pass and ask whether the sequence teaches the current task without an unexplained jump. Then perform a separate visual and audio pass.

Do not hide an important product change behind a seamless edit. If the difference affects what viewers can do, make the new instruction explicit.

## Choose how the published version will change

Check the host’s current replacement behavior before uploading. Some workflows preserve a URL, some create a new asset, and some offer choices that treat analytics differently. Do not assume an export with the same filename automatically replaces every published copy.

[Wistia’s replacement guide](https://support.wistia.com/en/articles/8274050-replacing-your-media) distinguishes overwrite from swap, including whether statistics continue or restart. It also notes that separate copies are not replaced automatically. Use the documented behavior for your actual host rather than treating those options as universal.

Decide whether the new version is a minor correction or a materially different recording for reporting purposes. If historical data continues, annotate the change in the team’s reporting notes so a retention chart spanning both versions is not interpreted as one unchanged video.

Inventory the destinations that matter: the primary watch page, embedded copies, shared host link, and any separately uploaded social versions. A replacement on one host does not update another platform’s upload.

Keep the previous source and edit through the normal recoverable asset process. A rollback should not require reconstructing the old video from a compressed public copy.

## Run the task with the updated video

Have someone use the revised recording to follow the current product workflow. Ask them to start from the documented condition and reach the shown result. This catches problems that a passive watch may miss, such as an omitted permission, an unexplained default, or a control that appears only in the editor’s account.

Check the published version rather than only the local export. Verify captions, chapters, thumbnail, links, and any player prompts. If the host preserves customizations, confirm that their old timing still fits the new cut.

Record the product version or verification date relevant to the repair and the segments changed. Keep the note practical: it should help the next editor know which part was recently checked, not imply the recording can never become outdated again.

Close with a bounded conclusion: the identified steps now match the verified workflow under the stated conditions. Do not claim the entire library is current because one video was repaired.

The finished work is a focused update with intact useful footage, accurate replacement segments, and a tested publishing path. Starting over remains an option when the core story changes, but it should follow from the repair map rather than habit.
