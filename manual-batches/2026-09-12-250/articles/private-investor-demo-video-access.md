Sharing an investor demo privately means deciding who may open it, then testing that decision from the viewer’s side. A link that works for you proves very little. Build a small access test before sending the recording, especially when it contains unreleased product behavior or material intended for one investment team.

## Write the audience boundary before choosing a link

Describe the intended audience in a sentence that someone else could enforce: “The two named partners and their associate may view this recording for their current product review.” That is more useful than “private investor link,” which leaves the recipient, purpose and onward sharing undefined.

Decide whether the associate can invite colleagues, whether downloads are acceptable and when you will review continued access. These are distribution choices for this recording, not a promise that the hosting service prevents copying. A viewer who can see and hear a video may still reproduce its contents.

Remove material that should not leave your control before uploading. Access settings are not a substitute for preparing an appropriate investor copy. If a recording needs extensive restrictions to be shareable, consider a narrower excerpt or a supervised discussion.

Create a neutral filename that identifies the product sequence and revision without exposing information in the title itself. Treat the thumbnail and description as part of the material you are sharing. The first visible frame should also be suitable for the intended audience.

## Match the sharing model to that boundary

Distinguish possession of a link from authorization tied to an identity. [YouTube’s visibility guidance](https://support.google.com/youtube/answer/157177?hl=en) explains that unlisted links can be reshared. Calling an unlisted recording “private” in an email does not turn it into named-recipient access.

For identity-based sharing, confirm which address the investor actually uses to sign in. Their public contact address may not be the account they use with your chosen service. Resolve that mismatch before a meeting, without relaxing the audience boundary simply to make an error message disappear.

[Google Drive’s sharing documentation](https://support.google.com/drive/answer/2494822?co=GENIE.Platform%3DDesktop&hl=en) describes named recipients and roles, and notes that folder permissions can affect access to a file. Inspect the containing folder as well as the recording. A carefully restricted file inside an overly broad location deserves another look.

Choose the least expansive arrangement that still supports the agreed review. If the recipient needs a downloaded copy, acknowledge that choice explicitly. Do not describe a download restriction, password or expiration date as protection against every possible form of capture.

## Run the six-viewer access test

Use this original worksheet for one exact recording revision. The results column must contain observations, not expectations copied from a settings panel. Conduct the test with accounts and devices you are authorized to use; do not borrow an investor’s credentials.

| Test identity or action | Intended result | Observation to record |
| --- | --- | --- |
| Named recipient | Opens the approved recording | Account used, prompt and playback result |
| Unexpected signed-in viewer | Cannot view | Whether video or metadata appears |
| Signed-out browser | Follows the selected boundary | Login, request-access or playback behavior |
| Forwarded link | Does not silently broaden access | Result using a non-recipient identity |
| Download attempt | Matches the agreed copy policy | Available controls and resulting file |
| Removed recipient | No new access through that identity | Fresh-session result after removal |

First test the named recipient path from a clean session. Play beyond the thumbnail; confirm that the expected revision actually loads and that audio works. Then test the unexpected and signed-out paths.

Forward the link only to your own authorized test identity. This simulates the effect of forwarding without distributing sensitive material to another person. If a real recording is too sensitive for testing, use a harmless file under the same configuration and repeat the essential checks on the final asset.

## Separate opening friction from an access defect

A blocked intended viewer and an admitted unintended viewer are different failures. The first interrupts review; the second crosses the audience boundary. Keep separate notes so a convenience fix does not quietly create a distribution problem.

For an intended viewer, record the account, device, browser and exact stage where access stopped. Did the invitation arrive? Did authentication complete? Did the page open but the player fail? Send a neutral troubleshooting instruction that addresses the observed stage.

For an unintended viewer, stop distribution while you inspect inherited permissions, general-link access and old copies. Do not keep sending the same link while investigating. Once corrected, repeat the negative tests rather than checking only that your preferred recipient can watch.

If the service or organization prevents the desired configuration, choose another agreed delivery route. That might be a different approved account or a scheduled viewing. Avoid claiming a configuration is private when the available settings cannot express your audience boundary.

## Make access removal a real rehearsal

Before relying on revocation, try it with your test identity. Remove access, open a fresh session and record what happens. Distinguish a new request from a player that was already open. Your observation should state exactly what you tested and when.

Then account for copies separately. Removing access to the hosted recording does not establish that a previously downloaded or independently captured copy has disappeared. If downloads were allowed, your distribution note should say so plainly.

A fictional team might record: “Named test viewer could open revision B. Unlisted test link admitted an unexpected viewer, so we changed the delivery arrangement. Fresh access failed after removal; previously downloaded material was outside this test.” That is an honest result, not a security certification.

Assign one founder to process access requests during the review window. Give that person the approved audience sentence and current revision identifier. They should not have to infer whether a new colleague is included from an ambiguous forwarded email.

## Send a viewing note that matches the test

Write a short message containing the recording’s purpose, duration, revision and expected sign-in identity. Explain how to request access for another viewer. If downloading is part of the arrangement, say what copy the recipient should keep and which earlier revision it replaces.

Do not put sensitive details into the troubleshooting message or access-request subject line. Keep the help path simple: “If this account cannot open the recording, reply with the address you want us to authorize.” Never ask for passwords or authentication codes.

After sending, save the worksheet with your private production notes. Recheck access after a revision, move to another folder or change in intended audience. Those events can invalidate a previous result even when the visible link looks familiar.
