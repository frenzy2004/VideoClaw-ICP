Show accelerator progress with two dated recordings of the same product task under comparable conditions. Preserve the earlier capture, repeat the input and starting state where possible, and make differences explicit. The paired footage should reveal what changed in the product, not merely that the newer video has better editing.

## Choose a change that a recording can establish

Start with a product behavior you expect to improve during the accelerator: completing a task without leaving the application, handling a previously unsupported input, or producing an inspectable result where the earlier build stopped. Choose something the camera can actually show.

Do not ask two clips to establish company-wide progress. A working interaction can demonstrate an implemented path; it cannot independently prove adoption, reliability across customers, or business impact. Keep the conclusion proportional to the recorded task.

[Techstars' mentor guidance](https://www.techstars.com/blog/founder-advice/five-things-every-techstars-mentor-should-know) emphasizes understanding founders' goals and how those goals are measured. A paired recording is one practical way to make a product milestone concrete during those conversations.

Write the comparison question before the first capture. For a fictional scheduling product: “Can a dispatcher move this job to a different technician without recreating it?” The question gives both recordings a common purpose. Avoid choosing the comparison only after discovering that the new footage looks more impressive.

## Preserve a baseline you will be able to repeat

Record the earlier build with its starting state visible. Save the fictional input, user role, relevant settings, and the sequence of actions. If the task depends on an external service, note which service and configuration were used without storing credentials in the media notes.

Keep the raw recording as well as any edited presentation version. A future comparison may need a few seconds that were omitted from the original cut. Do not rely on an application link alone as your archive of the baseline.

[Google Drive's version guidance](https://support.google.com/drive/answer/2409045?co=GENIE.Platform%3DDesktop&hl=en-419) explains how selected file revisions can be preserved. If you use it, distinguish your retained baseline from the newest file version; use equivalent explicit preservation in another storage system.

Capture enough context to recognize the task, but do not record unrelated customer data to make the baseline appear authentic. A carefully constructed fictional scenario can be repeated more safely and clearly than an uncontrolled production session.

If the old build is no longer available, use the genuine old recording. Do not reconstruct an intentionally clumsy “before” experience and present it as historical footage.

## Use a paired-capture protocol

Keep a small protocol beside both captures. Its purpose is not to make the product's environment artificially perfect. It makes meaningful differences visible and prevents editing choices from masquerading as engineering progress.

| Comparison element | Earlier recording | Later recording |
| --- | --- | --- |
| Task | Reassign fictional job J-17 | Reassign fictional job J-17 |
| Starting role | Dispatcher account | Dispatcher account |
| Starting state | Job assigned to technician A | Same logical state |
| Relevant input | Existing job and target technician B | Same input or disclosed replacement |
| Build and date | Record actual baseline identifiers | Record actual current identifiers |
| Completion evidence | Show final state or the point where work stops | Show the same completion criterion |
| Timing treatment | Note any cuts or speed changes | Use the same treatment or disclose the difference |

The example is fictional; substitute your own task rather than copying its identifiers into claims about your product.

Where conditions cannot match, add a difference row. A new device, integration, account role, or input size may be relevant. The reader can still learn from the pair when the comparison is qualified accurately.

## Record the new run without hiding the remaining work

Restore the agreed starting state and perform the same task in the current build. Keep the decisive action and result in one continuous capture when possible. If the new workflow still needs an operator intervention, preserve it rather than cutting directly to success.

Allow the product to behave as it does. If the first run fails, retain that source and decide whether the failure changes the claim you can make. A later successful run is still a successful example, but it is not evidence that the path works consistently in all conditions.

Do not exaggerate the baseline through narration. “Previously, this task required re-entering the job” is a bounded description if the old footage shows that. “The old product was unusable” is a much broader judgment and usually unnecessary.

Similarly, describe the new capability precisely. “This build preserves the job while changing the assignee” is clearer than “We rebuilt everything.” Your recording should make the improvement understandable even to someone who has not followed the accelerator week by week.

## Edit the pair around a shared action landmark

Choose a visible event that exists in both recordings, such as selecting the job or submitting the change. Align the clips around that event so the viewer can compare the subsequent sequence.

Use side-by-side playback only if both screens remain readable at the intended viewing size. Otherwise, play the baseline first, hold its result, and then show the new run with the same framing. Simultaneous playback is not automatically a better comparison.

Label each capture with its date and build context. If one clip reaches the result earlier, hold its actual final frame while the other continues, and identify the hold. Do not speed up only the newer clip while leaving the older one at normal speed.

A short original comparison caption might say: “Earlier capture: job details are entered again. Current capture: the existing job is reassigned.” Avoid adding a numerical speed claim unless you conducted an appropriate measurement separately. The edit's runtime is not the product's runtime.

## Present the improvement and its limit together

Introduce the pair with the comparison question, show the evidence, and finish with one sentence describing the observed change. Follow with the boundary that would matter to a reviewer: test environment, limited input type, manual setup, or a feature not yet rolled out.

Keep a private pairing note with the two source filenames, capture dates, input recipe, and alignment landmark. This makes the comparison reproducible when a mentor asks to see the complete run or a founder needs to update the presentation.

Do not overwrite the baseline simply because the new build is better. The historical capture is what makes this a progress demonstration rather than another standalone tour. Restrict access appropriately if either recording contains sensitive implementation context.

For a fictional team, the finished work product might be a short “reassignment before and now” clip plus two uncut source files. That is enough to support a focused accelerator discussion without turning every weekly update into a production project.
