Update an application demo by identifying exactly which recorded product behavior has changed, capturing a dated replacement, and using the accelerator's permitted update route. Preserve the submitted version privately. A new hosted file alone does not explain the change or guarantee that an application reviewer will see the replacement.

## Decide whether the old recording now misrepresents the product

Play the submitted demo before opening your editor. Write down what a reviewer could reasonably conclude from it today. Then compare that conclusion with the current product. A changed button color may not matter; a workflow that now works without the manual step shown in the recording may matter substantially.

Separate three situations. The product has improved, the product has changed direction, or the original recording was inaccurate. Improvement calls for a clear before-and-now explanation. A change of direction may require a new demonstration because the old task no longer represents the company. An inaccurate recording needs a correction, not a progress announcement.

Do not claim that any particular change qualifies for an application update under a program's rules. [YC's FAQ](https://www.ycombinator.com/faq) describes a material-update route rather than continuous editing after submission. Check the relevant accelerator's current process before sending or replacing anything.

Write one plain sentence describing the change. If it takes a paragraph to distinguish the new behavior from the old, narrow the update before recording.

## Build a scene replacement manifest

Use the old recording as an index. Identify the source time range, the behavior it shows, the current behavior, and whether the scene should remain, be replaced, or be retired. This keeps the edit tied to product evidence rather than a desire to make everything look newer.

Here is a fictional example for a dispatch product:

| Old scene | What it showed | Current state | Recording decision |
| --- | --- | --- | --- |
| Opening task setup | Dispatcher selects an unassigned job | Same task and role | Retain context if still accurate |
| Assignment step | Dispatcher copies a job identifier into another tool | Assignment now occurs inside the product | Capture the complete new action |
| Technician result | Technician refreshes to see the job | Result now appears through a different interaction | Record the actual current sequence |
| Closing label | Prototype status from the submission date | Different build and maturity | Replace with a dated, precise label |

Add a private column for the replacement source file. Keep timecodes tied to specific filenames: “00:28” is ambiguous when several cuts are open.

A completed fictional record could read: old file dispatch-A.mp4, 00:18–00:39, build A captured September 1 → dispatch-B.mp4, 00:16–00:34, build B captured September 10. Replace the assignment step; retain both source files. Destination: the dated supplement submitted through the program's currently permitted update route, with its receipt recorded after submission. These dates describe the example, not an actual application.

Do not preserve an old result shot merely because it looks clearer. If the new action produces a different result screen, capture that result in the same run.

## Record the change with enough unchanged context

A replacement clip needs a recognizable starting state. Show the same kind of task and identify the user role before demonstrating the new behavior. The viewer should not have to remember the old video perfectly to understand what changed.

When practical, use a comparable fictional input in the old and new demonstrations. If that is impossible, state the difference rather than implying a controlled comparison. For example, a new workflow using a different integration is not proof that the previous integration became faster.

Capture the action and result together. Avoid a sequence that starts after the new feature has already completed its important work. If setup remains manual, show or label that setup. If only part of the flow is implemented, distinguish that part from a prototype screen.

Record a short opening label with the product build or capture date. Keep it readable without letting it dominate the clip. The date provides orientation; it does not certify that the feature is generally available or that every account has the same behavior.

## Choose replacement, supplement, or a new destination

There are several ways to deliver updated media, and they have different consequences. A replacement changes what a link presents. A supplement leaves the original intact and adds a new explanation. A new upload may create a separate application attachment, depending on the system.

Follow the application's allowed path first. Do not silently swap content to create the impression that the revised behavior was present when the application was submitted. Even if the hosting service permits replacement, tell the reviewer what changed through the permitted channel.

[Google Drive documents file-version management](https://support.google.com/drive/answer/2409045?co=GENIE.Platform%3DDesktop&hl=en-419), including uploading revisions and preserving selected older versions. That is a storage capability, not an accelerator update policy.

Before replacing a hosted file, identify every important destination using that link. It may also appear in an interview invitation, a mentor message, or an internal review. Decide whether those destinations should now show the new version. If their context would become misleading, a distinct dated link may be clearer.

## Write a change note that accompanies the evidence

The note should make the reviewer able to understand the update without reconstructing your editing history. Include the original submission context, the product change, the new recording date, and the place to inspect it. Avoid restating the entire application.

A fictional change note could read: “Since our submitted demo, assignment now happens inside the dispatcher workspace. The new recording shows the same job moving from selection to the technician's queue. The opening label identifies the current build; the previous recording showed a manual transfer between tools.”

Add the actual approved link using the program's supported field or update mechanism. If only one segment changed, give its time range. If the new recording replaces the whole demonstration, say so directly.

Keep the wording within what the recording proves. One working demo does not establish deployment across all customers, production reliability, or a measured performance improvement. Explain any limits relevant to interpreting the clip, such as a test account or a feature enabled only for the demonstration.

## Verify the old and new paths after delivery

After the update, open the new destination as an intended viewer. Confirm access, title, date, complete playback, and the changed behavior itself. Do not stop at seeing the correct thumbnail.

Open the old path too. It should behave as you intended: retained with clear context, replaced through a disclosed update, or no longer shared where appropriate. A broken old link can be confusing if the application still points to it, so understand the portal's state before removing access.

Keep a private record of the original file, revised file, change note, and update confirmation. If the program provides no confirmation, record that uncertainty instead of assuming the reviewer received or watched it. Do not submit repeated updates merely to provoke acknowledgment.

This process ends when the new evidence is accurate and delivered through the authorized route, not when every old file has vanished.
