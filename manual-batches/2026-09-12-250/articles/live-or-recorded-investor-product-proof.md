Choose live, recorded, or hybrid product proof according to the investor's inspection job. Use live interaction when a new input matters, recorded evidence when a specific run needs clear viewing, and a labeled hybrid when both help. Decide the boundaries before the meeting so the audience knows what is happening in real time.

## Start with the question the format must answer

Write the product question in plain language. “What happens when this input changes?” may call for live interaction. “Can I inspect the complete operation you described?” may be served by a clear recording. “Which part is implemented?” requires accurate labeling whichever format you choose.

Do not choose live simply because it feels more impressive. A live screen can still contain prepared data, simulated responses, or hidden manual work. Nor should you choose recorded merely because it looks smoother. The important question is what evidence the format preserves.

[Sequoia's investor-presentation guidance](https://articles.sequoiacap.com/how-to-present-to-investors) discusses demos and workflows as ways to explain a solution. Treat format as a means of making that solution inspectable, not as the central performance.

Define the narrow claim you want the investor to understand. Then identify what they would need to see or change to examine it. That decision should precede production polish.

## Use live interaction when the new input is meaningful

Live interaction is useful when the investor can ask for a reasonable change and see the actual response. A filter, a different permitted record, or a supported configuration can reveal behavior that a fixed clip cannot adapt to.

Prepare the starting state and the allowed scope. Use a dedicated demo environment with fictional or permitted data. Do not let an investor's spontaneous request push the demonstration into production changes, sensitive records, or unsupported actions.

Keep the evidence readable while you operate. A real-time action that happens too quickly or outside the shared view may establish less for the audience than a well-framed recording. Pause on meaningful states and explain what they show.

State any preparation that materially affects the apparent behavior. A preloaded dataset or a manually approved request can be appropriate, but should not be mistaken for work completed during the visible interaction.

Live means the shown interaction is happening now. It does not mean the result is representative of every run or that the product is generally available.

## Use recorded evidence when a run needs careful inspection

A recording can preserve a complete physical operation, a long workflow, or a cross-device sequence in a view the investor can replay. It is especially useful when the evidence benefits from close framing or a visible comparison.

Identify the capture date, relevant environment, and any editing that changes timing or continuity. Keep an uncut source when the short version removes context that may become material to the discussion.

For remote playback, [Zoom supports sharing a local movie through its video player](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0064733). Use the actual delivery route in rehearsal and confirm that the investor receives the intended picture and sound.

Do not describe a prerecorded response as if it is being generated by a current input. Introduce the clip as a recording. If it is a selected successful run, keep that selection clear where it affects the claim.

Recorded proof can show what happened in a particular run. It cannot respond to a new question by changing the underlying event after the fact.

## Build a format decision matrix

Use a matrix that connects evidence needs to format rather than assigning one universal winner. The following is an original planning aid:

| Inspection job | Format to consider | Boundary to state |
| --- | --- | --- |
| Change a supported input during discussion | Live | Prepared environment and permitted interaction scope |
| Inspect a complete hardware operation | Recorded or live with adequate capture | Run conditions and any cuts |
| Understand a long processing sequence | Recorded | Time compression and actual elapsed time if relevant |
| Compare two device views from one event | Recorded or carefully rehearsed live | Synchronization and same-run identity |
| See a clear overview, then probe one detail | Hybrid | Exact transition from recording to live interaction |
| Inspect a design-only future interaction | Labeled prototype, either format | Design preview is not implemented execution |

Use the table to make a decision, not to justify a format you already prefer. If a row exposes missing evidence, capture or prepare that evidence before the meeting.

Keep production-resource choices separate. This decision does not determine whether you need an agency, editor, or new equipment. First establish the viewing job; resource selection is a different question.

## Make a hybrid transition unmistakable

A useful hybrid might begin with a recorded overview and then switch to a live test account for one investor-selected input. State that plan before the clip starts.

At the transition, identify the current screen and environment. “That was a recording from the test build; this is the same workflow running now in our demo account” is clear if true. Do not imply the live account inherits the recorded run's state unless it actually does.

Prepare the live starting point separately. A recording that ends with a completed task can make the audience expect the live view to begin there. Either align the scenario deliberately or explain the difference.

Keep questions about the recorded evidence answerable through replay. Do not force every follow-up into the live segment, especially when it concerns a specific earlier run. Similarly, do not answer a request for a new input by replaying the old one without explaining the limitation.

## Rehearse the chosen proof format with a bounded claim

Run the presentation in the selected format and ask a reviewer what they believe was live, recorded, implemented, or simulated. Repair any ambiguity before optimizing the delivery.

Check the first and last moments. The opening should identify the task and format; the ending should leave a readable result or a clear return to discussion. These boundaries matter as much as the middle of the demonstration.

Keep the source material and scenario notes that support the format. A recorded clip needs its matching source run; a live interaction needs a prepared test state; a hybrid needs an explicit connection between the two.

The decision is complete when the format makes the chosen claim inspectable under the meeting's conditions. It is not a guarantee against every technical issue, and it should not become a general live-demo recovery plan.
