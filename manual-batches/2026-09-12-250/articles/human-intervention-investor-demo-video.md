Show human intervention in an investor demo by recording the user-facing action and the operator's actual contribution as two connected parts of one workflow. Identify where responsibility changes, preserve meaningful waiting or edits, and show the real result. A polished interface should not imply that hidden manual work is already automated.

## Find the human action hidden by the interface

Walk through the product with the person who operates it. Ask what happens after the user submits a request, which steps software performs, and where a person makes a decision, supplies information, or completes the work.

List actions, not job titles. “Operator reviews the suggested match and chooses one” is useful. “Operations team involved” is too vague to guide a recording. Include manual setup when it materially affects the apparent capability.

[Paul Graham's essay on early manual work](https://paulgraham.com/ds.html) describes founders performing tasks they plan to automate later. That can be a real way of delivering a service; it should not be hidden in a video that appears to demonstrate current automation.

Separate a functioning human-assisted process from a simulated prototype response. In the former, the person really performs the work shown. In the latter, an example output may be supplied without executing the process. Label whichever is true rather than treating both as automatic product behavior.

## Choose the smallest operator view that explains the work

You do not need to expose a complete internal console. Identify the relevant request, decision, and action that connect the user input to the result. Capture only what a permitted viewer needs to understand that connection.

Use fictional or otherwise approved data. Operator screens often contain more sensitive information than the customer-facing interface, including other users, internal notes, or administrative controls. Prepare a bounded demonstration view before recording.

If showing the actual internal interface is inappropriate, use an accurately labeled explanation of the manual step and show the genuine user-facing result. Do not create a fake internal dashboard and imply it is the tool your team used.

Keep the operator's role clear. A founder narrating a demo may also be the person making the manual decision, but narration alone does not reveal that. State the intervention at the point where it occurs so the viewer can distinguish explanation from execution.

## Write a two-lane responsibility score

Map the visible user journey beside the actual operator or software work. The following fictional example is for a service that suggests appointment options:

| Stage | User-facing lane | Operator and software lane | Evidence to capture |
| --- | --- | --- | --- |
| Request | User submits preferred times | Software receives the request | Same fictional request identifier |
| Preparation | User sees a pending state | Software assembles candidate options | Actual prepared options, if relevant |
| Decision | Pending state continues | Operator chooses an appropriate option | Real selection action |
| Delivery | User receives the suggestion | Software sends the approved choice | Same option in the delivered result |
| Completion | User confirms | Product records the confirmation | Actual final state |

The score is an original planning aid, not a claim about any particular product. Replace every row with your actual process.

Mark the responsibility boundary precisely. If the software proposes and a person approves, show both. If the person creates the entire output, do not describe their action as a minor review.

## Capture both lanes from the same run

Start the relevant recordings before the user submits the request. Keep the same harmless identifier visible where possible. Record the operator's actual action and the resulting user state without substituting a prepared result from another attempt.

If the sources are separate, establish a shared reference that can be captured reliably. [Apple documents synchronization of same-take media](https://support.apple.com/en-ie/guide/final-cut-pro/verc1fabc30/mac). Whatever method you use, confirm alignment against the real sequence.

Do not pause one recording through the manual work and later align it as though no time passed. Preserve the source interval and disclose any time removed from the presentation cut.

The operator should use the actual supported process, not a special shortcut that changes what the demonstration claims to show. If a shortcut is necessary for the filming environment, explain it and narrow the claim accordingly.

Review the full run before editing. Confirm that the user input, operator action, and delivered result belong together. The shared identifier helps orientation, but the continuous sequence remains the stronger record of what happened.

## Edit the intervention into the story rather than a footnote

Introduce the task, show the request, and reveal the human step when the workflow reaches it. Then return to the user-facing result. This sequence gives the operator's work a clear causal role.

A brief side-by-side view can connect the lanes, but only if both remain readable. Sequential views may be better: user submits, operator acts, user receives. Use labels to keep roles clear across cuts.

Say exactly what the person does. “An operator selects the option before delivery” is more useful than “human in the loop.” The latter can cover anything from occasional oversight to doing the entire task.

If manual work takes longer than the clip can show, use a disclosed time jump. Keep the relevant action itself visible or explain the omitted work specifically. Do not cut from request to result while labeling only the product's processing time.

Avoid promising when the manual step will be automated. The recording's job is to explain the current process. Future plans require their own evidence and context.

## Test whether the viewer understands who did what

After playback, ask an unfamiliar reviewer to divide the work between the user, software, and operator. Do not give them the responsibility score first. Their explanation shows whether the edit communicated the actual boundary.

If they attribute the operator's decision to the software, repair the sequence or wording. If they think the person manually performed a step that is genuinely implemented, clarify that too. Honest attribution works in both directions.

Check the video's title, description, and closing line for broader automation claims that contradict the footage. A careful operator segment can be undermined by a headline that says the process is fully unattended.

Retain the source pair and the responsibility score with the final cut. When the product later changes, you can rerecord the affected boundary rather than assuming the old video now represents a more automated system.
