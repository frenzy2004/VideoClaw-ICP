A startup explainer video script should identify a recognizable problem, explain what the product does in plain language, show a concrete workflow, and offer one relevant next step. Write speech and visuals together, match every product statement to current evidence, and rehearse the script before deciding how long the finished video should be.

## Write the sentence that explains the product

Start with the person, the task, and the product’s action. Use this sentence as a draft: “[Product] helps [specific person] do [specific task] by [observable action].” Replace broad verbs such as transform or empower with something a viewer can picture.

If the product description requires several unfamiliar categories, explain the user path instead. What does someone bring into the product, what do they do, and what comes out? That sequence gives the script a concrete foundation.

YC’s Michael Seibel recommends clear, concise company descriptions and suggests walking through the user path when a simple explanation is difficult. His advice is written for pitching; the same clarity test is useful when drafting an explainer. [YC’s guidance on pitching a company](https://www.ycombinator.com/blog/how-to-pitch-your-company/).

Do not force the entire business into this opening sentence. The aim is to orient the audience so later details have somewhere to fit. Save company history and secondary use cases for another asset.

## Choose one problem at the moment it becomes visible

Describe a situation the viewer can recognize. For a fictional incident-handoff product, the situation might be an incoming teammate who can read the discussion but cannot identify who owns the next action. That is more specific than saying teamwork is broken.

Show the consequence without inventing a statistic. The teammate has to ask another question before proceeding. That observable interruption is enough to explain the problem. A numerical loss claim would require evidence beyond a fictional illustration.

Then state the product’s response at the same level of specificity. If the demonstrated feature displays ownership, explain ownership. Do not jump from that behavior to a claim that the product prevents every missed handoff.

Write a boundary beside the opening problem. Does it concern a particular team size, work pattern, or stage of the task? The boundary helps the editor avoid making a narrow example sound universal. Include it in the public script when it affects who should consider the product.

## Build a script with three working columns

Create columns for narration, visuals, and verification. The verification column stays with the production team; it helps determine whether the public sentence can be used as written.

| Narration purpose | Visual requirement | Verification question |
| --- | --- | --- |
| Name the user’s obstacle | Show the unresolved task | Is the scenario real, fictional, or reconstructed? |
| Explain the product action | Show the relevant control | Does the current release perform this action? |
| Show the result | Hold on the changed state | Does the state mean what the narration says? |
| Explain a condition | Show or state the prerequisite | Is the condition visible before the invitation? |
| Give the next step | Display the destination | Does the page offer what the script promises? |

Write one idea per row. If a sentence requires several unrelated screens, split it or narrow its claim. If a screen needs a long explanation, decide whether it belongs in a tutorial rather than the introductory film.

This worksheet is an original drafting tool. Its value is the connection between a spoken statement and something the viewer can inspect, not the number of rows.

## Adapt this complete fictional script

The following example describes an imaginary incident-handoff product. It is a writing demonstration, not a claim about VideoClaw or another available service.

“You are taking over an incident, and the discussion is long. Before acting, you need to know what is still open and who owns the next step.

“This incident-handoff workspace brings the current status, open questions, and named owner into one review.

“Here is a sample incident. Open the handoff, read the unresolved question, and select the teammate responsible for the next action. The updated owner appears beside the question so the incoming teammate can see where to begin.

“Your team still decides who should take responsibility. The workspace makes that decision visible; it does not make it for you.

“To explore this workflow, open the walkthrough linked beside this video.”

Pair the first paragraph with the problem scene, the middle paragraphs with the actual task, and the closing paragraph with the destination. When adapting it, replace every invented behavior with a feature you can demonstrate and every access statement with an offer that exists.

Read it aloud while performing the proposed screen actions. Notice where the viewer needs time to read. Cut an unnecessary sentence before increasing narration speed. The target is an understandable sequence, not a particular word count.

## Put meaningful visual information into the explanation

W3C describes integrated visual description as including necessary visual information in the main speaker’s script. It can be useful for instructional content when the narration naturally explains the important action or state. [W3C’s guidance on description of visual information](https://www.w3.org/WAI/media/av/description/).

For an explainer, replace vague pointers with precise language. “The owner appears beside the open question” conveys more than “you can see the improvement here.” The stronger sentence also tells the editor which visual must be readable.

Do not narrate every cursor movement. Describe the information needed to understand the task and its result. A navigation detail that does not affect the explanation can be omitted from an introductory film and covered in a tutorial.

Check visual labels against the spoken vocabulary. If the interface says “assignee” while the script says “owner,” explain the relationship or use consistent wording. Review the audio without looking at the screen to locate gaps, then verify those gaps against the full video.

## Revise the argument before polishing the language

Run a claim pass first. Circle every statement about speed, cost, outcomes, breadth, and availability. Ask which evidence supports the exact wording. A single successful demonstration supports a description of that demonstrated behavior, not an unlimited performance promise.

Next, run a comprehension pass. Give the script and rough visuals to someone who knows the problem area but not your product. Ask them what the product does and who should consider it. Note the words they use; a mismatch can reveal an unclear category or missing step.

Then run a spoken-language pass. Remove stacked nouns, repeated benefits, and sentences that require a second breath before the main verb. Keep the founder’s vocabulary where it helps explain the work.

Finally, check the close. If the audience has only learned what the product is, a detailed walkthrough may be a more natural invitation than a broad request to contact sales. Choose the next step based on the knowledge the video has actually supplied.

## Keep the script maintainable after launch

Save the narration, visual references, product capture date, and approved version together. Mark the sentences that depend on availability or a specific interface. Those are the first places to review when the product changes.

Make the core problem explanation separable from the replaceable demonstration. This lets the team update a changed workflow without rebuilding a still-useful introduction. Recheck the whole sequence afterward so the old narration does not imply something the new screens no longer show.
