A useful video production brief defines the audience, intended action, approved message, available sources, delivery package, review process, and budget boundary. Give every candidate the same brief and ask them to identify assumptions and exclusions. The template below makes those decisions explicit so proposals describe comparable work before production begins.

## Write the decision the video should support

Start with a person and a question. “Prospective operations managers need to understand how an exception is assigned” is more useful than “We need an exciting product video.” It tells a production partner what viewers should learn and what evidence belongs on screen.

Then name the next action. It might be watching a detailed demo, trying one workflow, or preparing a question for a sales conversation. Keep the action proportionate to the video's job. A short introduction should not carry the full burden of explaining implementation, pricing, and every feature.

Describe success as an observable communication outcome before discussing distribution metrics. For example, a reviewer unfamiliar with the product should be able to identify who uses it and explain the demonstrated task. That is a proposed acceptance test, not a promise of conversion or campaign performance.

Leave room for the partner's creative judgment. Specify the message and constraints, then ask for a treatment that serves them. A brief overloaded with shot-by-shot demands may remove useful choices before you have heard a better approach.

## Copy this production brief template

The following is an original working template. Replace each bracketed prompt with a decision, an asset link, or an explicitly assigned open question.

| Brief field | Fill-in prompt |
|---|---|
| Project and owner | [Working title, accountable owner, contact route] |
| Audience and situation | [Who is watching, what they already know, where they encounter it] |
| Viewer question | [The one question this video should answer] |
| Intended next action | [Specific action and destination] |
| Approved message | [Main statement, evidence, necessary qualification] |
| Sources available | [Footage, recordings, script, interviews, brand assets] |
| Work requested | [Writing, recording, editing, graphics, audio, versioning] |
| Delivery package | [Named versions, dimensions, captions, transcripts, editable materials] |
| Creative references | [Links plus what to borrow conceptually, such as pacing or clarity] |
| Review and approval | [Reviewers, final approver, review windows, revision boundary] |
| Schedule dependencies | [Source-ready date, first review, final approval, intended use] |
| Budget boundary | [Available range or ceiling, optional items, quote currency] |
| Restrictions and questions | [Sensitive material, asset permissions, prohibited claims, unknowns] |

Attach a source inventory beside the brief, not a pile of unexplained links. Give each asset a name, purpose, status, and owner. Mark unfinished recordings as pending and state when they will arrive.

Ask every provider to return the brief with assumptions annotated. If someone proposes a different delivery package, request it as a clearly separated alternative. That preserves the baseline comparison while allowing a useful creative recommendation.

## Make the delivery package testable

“Social cutdowns” is too vague to price or approve. Specify how many distinct stories you need, which formats they require, and whether the editor must adapt the composition or simply supply a different frame. Name the intended destinations without assuming one file works everywhere.

Describe captions, transcripts, and important visual explanation in the package. W3C recommends putting accessibility requirements into internal project requirements, requests for proposals, and contracts. That makes accessibility a planning decision instead of a surprise request at export. [W3C audio and video planning](https://www.w3.org/WAI/media/av/planning/).

For each deliverable, write a short acceptance condition. A product lesson might require legible interface labels, accurate narration, reviewed captions, and an ending that identifies the next task. Give the editor the factual reference and name the person authorized to resolve discrepancies.

Ask which editable materials will be included and what another operator needs to use them. If you only require finished videos, say so deliberately. If future interface changes are likely, discuss reusable project materials before the proposal is finalized.

## Supply evidence and protect the source boundary

Separate material the team may use from material included only as background. A private customer conversation may help explain an issue without being approved for inclusion. Use asset statuses such as approved for this project, reference only, and awaiting decision.

For product claims, provide the current wording and the evidence owner. An editor should be able to flag a stronger-sounding phrase without having to decide whether it is true. Give the approver a practical route to answer factual questions during production.

Limit the source package to what the assignment needs. FTC guidance recommends restricting contractor access to sensitive information that is unnecessary for their work. [FTC guidance on access and service providers](https://www.ftc.gov/business-guidance/resources/start-security-guide-business).

Apply that principle by supplying demonstration recordings with fictitious account information where appropriate. Remove irrelevant customer conversations from the editing package. Keep a company owner for transfer access and any later questions about source use.

## Review a fictional completed brief

Here is a fictional example for a startup called FieldRelay. Its audience is an operations manager evaluating whether a missed handoff can be assigned clearly. The viewer question is: “How does an unresolved request reach the right teammate?”

The requested video follows one demonstration request from intake to assignment. The product lead supplies the recording, approves the interface labels, and identifies the last screen that proves completion. Marketing supplies a short narrative and the destination for the next action.

The delivery package contains one main demonstration and one shorter introduction. The shorter version must still identify the user, show the request, and preserve the outcome. The team asks candidates to quote custom animation separately because the current recording may explain the process without it.

The open question is whether the source recording makes the assignment status readable. The brief assigns the product lead to supply a new close-up if needed. That is more useful than letting each provider silently assume the missing shot will appear.

Before sharing, FieldRelay asks someone outside the project to read the brief and describe the requested result. Any disagreement becomes a brief correction rather than a late editing instruction.

## Turn proposals into a clear kickoff

Read proposals against the brief one field at a time. Look for missing source preparation, unassigned approvals, optional deliverables presented as included, and deadlines that assume immediate feedback. Ask questions in writing so the accepted version contains the answer.

Choose the baseline deliverables before scheduling production. Record the agreed scope and preserve the optional ideas for later decisions. If a creative recommendation changes the main message or intended audience, revise the brief and get the relevant owner to approve that change.

At kickoff, confirm the source-ready date, first review package, one feedback coordinator, and the point at which additional work needs a new estimate. Walk through one likely exception, such as a late screen recording. Establish who decides whether to replace it, delay delivery, or simplify the story.

Keep the brief short enough to use during review. It should remain the reference for acceptance rather than becoming a document everyone forgets after procurement.
