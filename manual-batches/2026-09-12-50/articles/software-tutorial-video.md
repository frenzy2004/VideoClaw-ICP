Make a software tutorial video by defining one task, verifying its steps in a clean example account, and recording the actions with clear narration. Show the starting state and successful result, include useful recovery guidance, and test the finished lesson with someone who has not already learned the workflow.

## Turn the topic into a testable task

“Reporting features” is a topic. “Create a saved view of requests assigned to your team” is a task with a recognizable finish. Start with the task because it tells you what must appear in the recording and what can be left for another lesson.

Write an acceptance sentence: “A viewer with the stated access and sample data can create the named view and recognize that it was saved.” This is an editorial planning tool, not a promise about how every learner will perform.

List prerequisites separately: relevant role, account state, product version, and necessary data. Decide whether to teach those prerequisites or link to existing instructions. A tutorial that silently assumes preparation leaves viewers unable to reproduce the demonstration.

Choose a title that names the task and scope. If the lesson covers only a specific account configuration, say so where it affects the procedure. Avoid claiming to be a complete guide when the video teaches one route through a larger product.

## Verify the procedure before scripting it

Perform the task from the intended starting point and write down every meaningful action. Include the final save, apply, or confirmation step. Check which actions depend on earlier choices and where the interface can display an alternative state.

Microsoft's style guide recommends numbered steps, clear action locations, and instructions that include the actions needed to complete a procedure. [Microsoft's step-by-step instruction guidance](https://learn.microsoft.com/en-us/style-guide/procedures-instructions/writing-step-by-step-instructions). Apply those principles to the working outline before recording.

Use a demonstration environment with fictional data. Reset it between takes so the result is actually produced by the actions shown. If a saved view already exists from rehearsal, a second take might appear to work while hiding the step that creates it.

Make a note of asynchronous events such as loading or processing. Decide whether to show the wait, shorten it with an explicit transition, or explain it verbally. Do not edit a slow operation to look instantaneous when that difference would confuse a learner following along.

## Build a screen-and-narration script

Write what the viewer hears beside what they see. This exposes instructions that name a control before it appears or describe a result after the screen has moved on. Keep one purposeful action in focus at a time.

The following original script worksheet uses a fictional request-management application. Interface names are invented for the exercise.

| Step | Screen state | Narration purpose | Proof of completion |
| --- | --- | --- | --- |
| Orient | Requests page with sample records | Name the task and required role | Viewer recognizes the starting page |
| Filter | Owner filter opened | Explain which team to select | Only the intended team's records remain |
| Save | Save view dialog visible | Name the view and confirm the action | New view appears in navigation |
| Reopen | Another page, then saved view | Show that the saved choice persists | Same filter and view name return |
| Recover | Help route for missing controls | Explain what to do without access | Viewer has a specific next step |

W3C describes integrated visual description, where the main narration conveys visual information necessary to understand a video. [W3C's visual-description guidance](https://www.w3.org/WAI/media/av/description/). In this example, say which filter changed and what confirmation appeared; “click here” and “there it is” omit the information a listener needs.

Read the script aloud while performing the actions. Remove wording that forces you to rush the screen. Where an explanation is longer than the action, hold a relevant state or introduce the concept before demonstrating it.

## Record for clear correction and reuse

Set up the visible workspace before capturing. Close unrelated windows, remove personal notifications, and use consistent sample names. Check a short recording for understandable audio and readable interface text before completing the full lesson.

Record in manageable sections with clear starting and ending states. Leave enough room around an action for an editor to make a clean join. When a step fails, reset the example and record the complete action again rather than stitching together incompatible states.

Keep pointer movement purposeful. Move to the control being explained, pause long enough to establish its location, and show the result. Avoid circling the screen while discussing a concept that has no visual counterpart.

Capture a clean version of the important product action. If you also want a presenter introduction, keep its role specific: explain who the lesson helps and what it teaches. A presenter window that covers a required control works against the tutorial's purpose.

Record the product version and source date with the project files. This helps future editors decide whether a new interface requires a small replacement or a new lesson.

## Edit for reproducibility

Use the verified procedure as an editing checklist. Every required action should appear in the correct order, and every important result should be visible. Remove irrelevant delays and mistakes while preserving the information a learner needs to reproduce the task.

Make any skipped time understandable. For example, an editorial note can explain that processing continues before the next scene. The note should describe the omission without implying a universal duration that has not been established.

Review the narration and picture together after adding zooms, captions, or emphasis. A zoom can improve a control's readability while removing the navigation context that tells the viewer where they are. Keep enough orientation to make the close-up useful.

Prepare a written companion with the same task title, prerequisites, steps, and confirmation. Include a recovery route for the most relevant alternative state. This companion is especially useful when the viewer returns to one step later and does not need the entire recording again.

Separate reusable concepts from interface-dependent instructions. An explanation of why to save a view may remain useful after a button moves. Keeping those sections distinct makes a targeted refresh possible without reusing outdated screen guidance.

## Test the lesson with a fresh learner

Give a reviewer the video, companion instructions, and a clean example environment. Ask them to complete the task without additional coaching. Tell them they can stop or request help; the purpose is to find missing instruction, not to test their persistence.

Record the step where difficulty occurs, what the viewer expected, what appeared, and what assistance resolved it. Distinguish a content omission from a product issue. If the control is unavailable to the stated role, the prerequisites or the procedure need correction.

Afterward, ask the reviewer to explain how they know the task succeeded. A viewer can reach the right screen accidentally without understanding the confirmation. If that happens, strengthen the result explanation and test the affected section again.

Publish only the version that matches the reviewed procedure. Set a maintenance trigger for changed controls, changed prerequisites, or repeated confusion. Keep a route for reporting outdated instructions near the lesson so a future mismatch becomes visible to the owner.
